# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

lohn.cc is a one-man software house's internal CRM/ERP platform, built modularly so each business module can later ship separately as SaaS. Targets the Laos market (LAK is the default currency throughout). Live production instance: https://app.lohn.cc.

## Commands

Package manager is pnpm (`packageManager: pnpm@12.4.2` — pnpm isn't installed system-wide by default; if missing, install to a user prefix rather than requiring sudo: `npm install -g pnpm --prefix ~/.local`, `~/.local/bin` on PATH).

```
pnpm install                              # install all workspace deps
pnpm db:generate                          # generate a Drizzle migration from schema changes (packages/db)
pnpm db:migrate                           # apply pending migrations
```

**`turbo run dev` / `turbo run build` / `turbo run typecheck` fail with `Exec format error` in sandboxed dev environments** (confirmed on this machine's setup) even though the same binaries run fine invoked directly. Don't debug this further — bypass turbo and run per-package commands directly:

```
cd apps/web && ./node_modules/.bin/next dev -p 3000      # dev server
cd apps/web && ./node_modules/.bin/next build             # production build
./node_modules/.bin/tsc --noEmit -p packages/db            # typecheck a single package
./node_modules/.bin/tsc --noEmit -p packages/auth
cd apps/web && ../../node_modules/.bin/tsc --noEmit        # typecheck the web app (uses its own tsconfig)
```

No test suite exists yet.

### Local Postgres

```
podman-compose -f infra/podman-compose.yml up -d
```

Runs `postgres:16-alpine` on host port **15432** (not 5432 — that port is used by an unrelated native systemd Postgres instance on this machine for a separate purpose), with default credentials `lohn:lohn@localhost:15432/lohn`, bind-mounted to `podman-data/postgres/` (gitignored). `packages/db/src/client.ts` and `drizzle.config.ts` both default to this URL when `DATABASE_URL` is unset.

### Production deployment (this machine)

The live app is **not** run via `next dev`. It runs a production build (`next build && next start`) as a `systemctl --user` service (`lohn-web`, lingering enabled so it survives logout/reboot), fronted by a system-level `cloudflared` service tunneling `app.lohn.cc` → `localhost:3000`. After changing app code that needs to go live:

```
cd apps/web && ./node_modules/.bin/next build
systemctl --user restart lohn-web
```

This split matters: Next's dev server actively blocks cross-origin requests (including from the tunnel's public hostname), which silently breaks real sign-in/sign-up traffic. Never point the public tunnel at `next dev`.

## Architecture

**Monorepo**: pnpm workspaces + Turborepo. `apps/web` (Next.js 16, App Router) is the only app; `packages/db` (Drizzle ORM schema + Postgres client) and `packages/auth` (Better Auth server config + React client) are shared internal packages, not separately published.

**Tenancy**: Better Auth's `organization` plugin (`packages/auth/src/server.ts`) *is* the tenant model — there is no separate "tenant" or "account" table. Every business table has an `organizationId` column referencing `organization.id`. Every mutating server action derives the org from `session.session.activeOrganizationId` (set server-side from the signed session cookie) and scopes its `WHERE` clause with it — **never** accept an `organizationId` from client input. A forged id in a mutation's payload should match zero rows, not another tenant's data.

**Schema**: `packages/db/src/schema/` has one file per module (`auth.ts` — generated, see below; `crm.ts`; `erp.ts`), barrel-exported from `schema/index.ts`. New modules follow the same shape: tenant-scoped `pgTable`, `text("id").primaryKey().$defaultFn(() => crypto.randomUUID())`, snake_case columns, `createdAt`/`updatedAt` timestamps, and a `relations()` block if the module needs `db.query.*` joins (e.g. invoice → items → contact). After adding/changing a table: `pnpm db:generate` then `pnpm db:migrate` (Postgres must be running).

Within `packages/db` and `packages/auth`, use **extensionless** relative imports (`./schema/index`, not `./schema/index.js`) — the `.js`-extension form breaks `drizzle-kit`'s config loader in this repo, since `tsconfig.base.json` uses `moduleResolution: Bundler`.

`packages/db/src/schema/auth.ts` is generated by the Better Auth CLI from the config in `packages/auth/src/server.ts` (`npx @better-auth/cli generate` from `packages/auth/`, output to `../db/src/schema/auth.ts`) — don't hand-edit it; change the auth config and regenerate instead.

**Cross-package env var gotcha**: `NEXT_PUBLIC_*` vars do NOT get inlined into workspace packages resolved through `node_modules` (e.g. `@lohn/auth`) unless those packages are listed in `apps/web/next.config.ts`'s `transpilePackages`. Without it, code in a shared package silently falls back to any hardcoded default instead of the real env value — this broke the auth client's `baseURL` in production once already.

**Auth**: Email/password only, **`disableSignUp: true`** — the platform is invite-only (one real account exists; there is no self-serve signup flow in production). `/sign-up` shows a static "invite-only" message rather than a form. Session cookies: `__Secure-` prefixed, `HttpOnly`, `Secure`, `SameSite=Lax`, 7-day expiry, all Better Auth defaults. Rate limiting is on by default in production (`next start`), off under `next dev`.

**Routing**: `apps/web/src/app/(app)/` is a route group for everything behind auth (`/`, `/crm`, `/crm/board`, `/erp`) — its `layout.tsx` checks the session once and `redirect("/sign-in")`s if missing, and renders the shared `NavBar`. Pages inside only need to handle the "no active organization yet" case themselves. `/sign-in`, `/sign-up`, `/api/auth/[...all]`, and `/invoice/[id]` live outside the group and are intentionally public.

**Public invoice links** (`/invoice/[id]`): access control is the invoice's own `crypto.randomUUID()` primary key acting as an unguessable bearer token — same model as e.g. Stripe payment links. No separate token field, no auth check on that route. Keep it that way; don't add a sequential ID scheme to any publicly-linkable table.
